# 06 — Дорожная карта MVP

Поэтапный план сборки v3 с нуля (в отдельном проекте). Каждый этап — самостоятельно проверяемый.

**Процесс — BDD ([07](07-bdd.md)).** Каждый этап ведём циклом: согласовать `.feature`-сценарии → красный прогон → реализация домена → зелёный. «Готово, когда…» ниже = соответствующие `@stageN`-сценарии из [`features/`](features/) зелёные. Привязка фич к этапам — в [таблице 07](07-bdd.md#карта-фич-по-этапам).

## Порядок и зависимости

Этапы упорядочены так, чтобы каждый опирался только на уже готовое, и при этом как можно раньше собрать сквозной продуктовый поток (анкета → подбор → лист), а реализм наличия добавить следом.

```
0 Каркас (clock) ─► 1 Схема+Festival+импорт ─► 2 Движок+предрасчёт+активация ─┐
                                            └─► 3 Аккаунты/безопасность/анкета ┤
                                       (2 и 3) ─► 4 Подбор+маршрутный лист ────┘
4 ─► 5 Наличие+эмуляция ─► 6 Уведомления
                       └─► 7 Импорт наличия из файла
```

Два «шва» — сознательно вводятся позже, чтобы не блокировать продуктовый поток:

- **Наличие — шов.** Движок (этап 2) и подбор (этап 4) строят хук фильтрации наличия как **pass-through (всё в продаже)**; реальная динамика наличия, отсев распроданных и алерты появляются на **этапе 5**. Поэтому сценарии, зависящие от наличия (отсев распроданных, «только доступные»), живут в `availability.feature` и зеленеют на этапе 5.
- **Создание фестиваля — CLI раньше UI.** На этапах 1–2 фестиваль создаётся и наполняется через CLI/`batch` (`importing/seed.py`, предрасчёт), т.к. аккаунтов/RBAC ещё нет. Админ-UI «Создать фестиваль / активировать» появляется на **этапе 3** (с RBAC) поверх той же доменной логики.

## Этап 0 — Каркас

- Репозиторий, структура модулей ([05](05-architecture-and-platform.md)), Docker Compose (`app` + `db`), нестандартные порты.
- Конфиг (`config.py`), `.env`, пины версий (fastapi/starlette/pydantic совместимы), Alembic.
- `FestivalClock` (real/offset/accelerated) + `ClockState` + тесты времени.
- **Готово, когда:** приложение поднимается, миграции применяются, часы переключают режимы.

## Этап 1 — Доменная схема, фестиваль и импорт каталога

- `Festival` + скоуп `festival_id` по всем сущностям ([02](02-domain-model.md#фестиваль-и-скоупинг), [ADR 0007](adr/0007-single-db-festival-scoping.md)); инвариант «один активный».
- Сущности из [02](02-domain-model.md): каталог + Program (повторы) + FestivalDay.
- Создание фестиваля (`status=draft`) и импорт — пока через **CLI/`batch`** (`importing/seed.py`: Excel → каталог + Purchase **в рамках фестиваля**, идемпотентно по `(festival_id, ключ)`, пути из конфига). Админ-UI для этого появится на этапе 3 (нужен RBAC).
- **Готово, когда:** админ создаёт фестиваль и импортирует его данные; концерты/залы/переходы/программы/покупки в БД со скоупом `festival_id`; `show_num` и `crm_show_id` раздельны.

## Этап 2 — Движок маршрутов (офлайн + ранжирование)

- `domain/routing`: DAG, перечисление дневных маршрутов, агрегаты, признаки, Pareto-отсев, архетипы (перенос GMM).
- **Фаза предрасчёта по ВСЕМ дням фестиваля** (`batch/` итерирует `FestivalDay` фестиваля) — шаг 3 конвейера создания фестиваля; в v2 был только один день, см. [03](03-route-engine.md#когда-и-для-каких-дней-считаем).
- **Активация фестиваля** (`draft → active`) после ревью предрасчёта — гейт перед публикацией ([05](05-architecture-and-platform.md#жизненный-цикл-фестиваля)).
- `evaluate_transition` с порогами из конфига.
- Ленивая top-k сборка по дням; хук фильтра наличия — **pass-through (всё в продаже)** до этапа 5 (см. «шов наличия» выше).
- **Готово, когда:** дневные маршруты с признаками построены **для всех дней фестиваля**; фестиваль можно активировать; есть top-k фестивальных (многодневных) по заданным весам (юнит-тесты на комбинирование/конфликты).

## Этап 3 — Аккаунты, безопасность и анкета

- Регистрация/вход/logout, RBAC (`require_role`), управление ролями (admin).
- Безопасность ([08](08-cross-cutting.md#безопасность)): CSRF на мутациях, rate-limit/lockout, сброс пароля, верификация email; согласие на обработку ПДн при регистрации ([приватность](08-cross-cutting.md#приватность-и-персональные-данные-152-фз)).
- 4-шаговая анкета → `UserPreferences` → веса ([03](03-route-engine.md#анкета-и-веса)).
- **Готово, когда:** зритель регистрируется (с согласием), проходит анкету, веса влияют на выдачу; `auth_roles`/`security`-сценарии зелёные.

## Этап 4 — Подбор и маршрутный лист

- Экран подбора: архетипы + top-k карточки (референс `Route list example`, `Route characteristics`).
- `RouteSheet`/`RouteSheetItem`: создать из архетипа / с нуля; add/remove; pin.
- Показ сложностей (переходные карточки, статусы); детект повторов программ.
- Подсказки дополнения ([03](03-route-engine.md#подсказки-дополнения)).
- HTMX-интерактив (добавление без перезагрузки).
- **Готово, когда:** зритель собирает и правит лист, видит накладки/переходы/повторы, получает релевантные подсказки.

## Этап 5 — Наличие и эмуляция

- `ConcertAvailability` + `AvailabilitySnapshot`; модели `sim_curve` и `sim_replay`.
- **Замыкание «шва наличия»:** хук фильтра (этапы 2/4) перестаёт быть pass-through — отсев распроданных дневных маршрутов и «только доступные» в подборе становятся реальными (сценарии в `availability.feature`).
- Планировщик: тик наличия от `FestivalClock`; инвалидация кэша маршрутов.
- Пульт эмуляции (admin): режим часов/наличия, прыжок к фазе, ручной тик.
- **Готово, когда:** в `accelerated` наличие меняется во времени, распроданные концерты уходят из подбора; реплей реальных покупок воспроизводит таймлайн продаж.

## Этап 6 — Уведомления (скелет)

- `OutboxMessage` + диспетчер в планировщике; email через SMTP.
- События `concert_reminder`, `availability_alert`.
- **Готово, когда:** в `festival`/`accelerated` напоминания ставятся и «отправляются» (лог/почта), весь цикл проверяется за минуты.

## Этап 7 — Импорт наличия из файла (продакшн-путь)

- `importing/availability.py`: периодическая загрузка файла остатков → `ConcertAvailability` (`crm_import`).
- **Готово, когда:** загрузка файла обновляет наличие и подбор без перезапуска.

## После MVP (зона роста, приоритет по обсуждению)

1. **Разложение купленного по людям** (CRM) — несколько листов на пользователя, граф конфликтов.
2. **Исследователь:** дашборды, маркетинг-фильтры, «интересные факты», пост-фактум аналитика продаж (на `AvailabilitySnapshot`).
3. **Telegram-бот + массовые рассылки** → ввод Celery/RabbitMQ; диспетчер outbox переключается на брокер.
4. **Live-API CRM** вместо файлов (наличие и покупки).
5. **Персонализация на покупках** — обучение предпочтений по реальным `Purchase`, веса под зрителя.
6. **Полный CRUD-админ** по сущностям каталога.

## Критерии готовности MVP (definition of done)

- Зритель: регистрация → анкета → подбор → собранный маршрутный лист с понятными сложностями.
- Админ: импорт каталога, запуск предрасчёта, пульт эмуляции, переключение режимов наличия.
- Время управляемо; реальные данные не затираются; логика не дублируется между слоями.
- Стек: FastAPI+HTMX+Postgres, без брокеров; миграции; пины версий.
- Сквозное ([08](08-cross-cutting.md)): базовая безопасность (CSRF, rate-limit, сброс пароля) и приватность (согласие, псевдонимизация в аналитике) на месте; структурные логи и ключевые метрики; перф-бюджеты соблюдаются на нагрузочном прогоне через `accelerated`-часы.
- Тесты: `@mvp`-сценарии behave зелёные + юнит-тесты алгоритмики; CI гоняет behave+pytest и линт «нет прямого `datetime.now()`».
