# 08 — Сквозные аспекты

То, что пронизывает все модули и было пропущено в первой редакции: приватность, безопасность, наблюдаемость, производительность, CI и пирамида тестов. Эти требования закрываются своими сценариями (`@security`, `@privacy`) и юнит-тестами.

## Приватность и персональные данные (152-ФЗ)

Сервис обрабатывает ПДн: email, имя, а также покупки из CRM (`Purchase.customer_external_id` → конкретный человек). Это обязывает к минимальной дисциплине ещё в MVP.

- **Минимизация.** Храним только нужное. `customer_external_id` — псевдоним из CRM, не ФИО/телефон. Связь «псевдоним → личность» остаётся в CRM, не в Figaro.
- **Согласие.** При регистрации — явное согласие на обработку ПДн и ссылка на политику. Флаг `consent_at` на `User`.
- **Назначение.** Покупки используются для: реплея наличия, разложения по людям (зона роста), будущей персонализации. Не для рассылок без отдельного согласия (маркетинговое согласие — отдельный флаг).
- **Ретеншен.** Политика хранения: покупки/аккаунты — срок X после фестиваля, затем удаление/обезличивание. Зафиксировать X с заказчиком.
- **Право на удаление.** Эндпоинт/процедура удаления аккаунта и связанных данных.
- **Псевдонимизация в аналитике.** Дашборды исследователя ([роль `researcher`](05-architecture-and-platform.md#роли-и-доступ-rbac)) работают на **агрегатах/псевдонимах**, без прямого доступа к email/именам. Запрет джойнить ПДн с аналитикой на уровне доступа.
- **Транзит/хранение.** TLS снаружи; секреты — в окружении, не в репозитории; пароли — argon2/bcrypt.

## Безопасность

- **CSRF.** HTMX шлёт обычные формы/POST → нужен CSRF-токен на мутациях (Origin-проверка + токен в форме/заголовке `X-CSRF-Token`).
- **Аутентификация.** Сессия или JWT в httponly+secure+SameSite cookie; **logout** инвалидирует сессию; срок жизни + перевыпуск.
- **Брутфорс.** Rate-limit и lockout на вход и на сброс пароля (по IP и по аккаунту).
- **Восстановление доступа.** Сброс пароля по одноразовой ссылке с TTL; **верификация email** при регистрации.
- **Авторизация.** Единая зависимость `require_role` ([05](05-architecture-and-platform.md#роли-и-доступ-rbac)); проверка владения ресурсом (зритель правит только свои `RouteSheet`).
- **Ввод.** Валидация и экранирование (Jinja автоэкранирование вкл.); загрузка файлов (импорт остатков) — только admin, проверка типа/размера.
- **Заголовки.** CSP, HSTS, X-Content-Type-Options, X-Frame-Options.
- **Аудит.** Лог действий admin (пульт эмуляции, импорт, смена ролей).

## Наблюдаемость

- **Логи** структурные (JSON), с `request_id`/`correlation_id`; без ПДн в логах.
- **Метрики** (Prometheus-совместимые): латентность подбора (p50/p95/p99), время пересборки наличия и инвалидации кэша, размер outbox и доля доставленных уведомлений, ошибки 4xx/5xx.
- **Трейсинг** ключевых операций (подбор top-k, тик наличия) — опционально, но точки разметить.
- **Бизнес-метрики:** заполнено анкет, создано листов, среднее число концертов в листе — питают исследователя позже.

## Производительность и нагрузка

Ориентир: ~5000 зрителей за фестиваль → десятки одновременных запросов. Бюджеты (цели для нагрузочного теста):

| Операция | Цель |
|----------|------|
| Подбор маршрутов (top-k под анкету) | p95 < 300 мс на запрос (из тёплого кэша доступных дневных) |
| Добавление концерта в лист + проверка конфликтов | p95 < 150 мс |
| Полный пересчёт наличия (тик) | < 2 с на весь каталог |
| Инвалидация + прогрев кэша доступных дневных | < 1 с |

**Нагрузочный тест** прогоняем через `accelerated`-часы ([04](04-simulation-and-availability.md)) в фазе `festival`: имитируем пик заходов + поток тиков наличия и уведомлений за минуты. Тяжёлый предрасчёт дневных маршрутов — офлайн, вне горячего пути.

## CI/CD

- На каждый PR: `behave -t @mvp -t ~@wip` (приёмка) + `pytest` (юниты) + линтеры.
- **Линт-правило «нет прямого времени»:** запрет `datetime.now()/utcnow()/time.time()` в `domain/`/`services/` (только через `FestivalClock`). Реализуется flake8-плагином/ruff-правилом или grep-гейтом.
- Миграции Alembic применяются на чистой БД в CI (проверка отсутствия дрейфа схемы).
- Сборка Docker-образа; прогон smoke против поднятого контейнера.

## Пирамида тестов (чтобы не «гёркинизировать» всё)

BDD — не единственный уровень. Распределение:

```
        ╱ web smoke (тонкий) ╲        — пара сценариев @web: страница открывается, форма шлёт HTMX-запрос
      ╱  BDD / приёмка (behave) ╲     — поведение и правила, на доменном уровне (большинство .feature)
   ╱      юнит-тесты (pytest)      ╲  — алгоритмика: top-k корректность, математика кривой распродажи,
  ╱________________________________╲   формула конфликтов, агрегация признаков, Pareto
```

Правила:
- **Алгоритмику и числовые крайние случаи** покрываем юнит-тестами (быстро, точно), а не Gherkin.
- **BDD** описывает наблюдаемое поведение и бизнес-правила; бьёт по `domain`/`services`, не по HTTP.
- **Веб** — минимум `@web`-сценариев (рендер, базовый HTMX-цикл), без дублирования доменной логики.
- Один уровень — одна ответственность; не тестируем одно и то же на трёх уровнях.
