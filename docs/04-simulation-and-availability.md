# 04 — Часы фестиваля, эмуляция и наличие

Это сквозная подсистема, а не тестовый хак. Она даёт: разработку/демо в состоянии, близком к реальному; проверку уведомлений и нагрузки в «дни фестиваля»; пост-фактум аналитику «как продавалось».

## Принцип: время только через `FestivalClock`

Запрет на прямой `datetime.now()/utcnow()` в доменном и прикладном коде (линт-правило/код-ревью). Всё «сейчас» — из единого провайдера.

```python
class FestivalClock:
    def now(self) -> datetime: ...     # текущее «виртуальное» время
    def mode(self) -> ClockMode: ...   # real | offset | accelerated
```

Режимы:
- **real** — `now() == системное время` (продакшн на самом фестивале).
- **offset** — `now() = real + Δ` (например, «мы за 14 дней до фестиваля»). Фиксированный сдвиг, время идёт обычной скоростью.
- **accelerated** — `now() = anchor_virtual + (real − anchor_real)·K`. Виртуальное время бежит в `K` раз быстрее (час за минуту и т.п.).

Состояние часов персистентно (таблица `ClockState`: `mode`, `anchor_real`, `anchor_virtual`, `speed K`) — переживает рестарты, общее для всех воркеров.

## Фазы фестиваля

Производная от `clock.now()` и дат `FestivalDay`:

| Фаза | Когда | Что активно |
|------|-------|-------------|
| `pre_sale` | до старта продаж | каталог виден, наличия нет |
| `on_sale` | продажи идут, до 1-го дня | наличие меняется по выбранной модели; подбор маршрутов |
| `festival` | в течение дней фестиваля | напоминания «скоро ваш концерт», нагрузка |
| `post` | после | аналитика, пост-фактум графики |

Фазу читают: модель наличия, планировщик уведомлений, UI (баннеры «до фестиваля N дней»).

## Модель наличия билетов

Наличие живёт в `ConcertAvailability` (+ история `AvailabilitySnapshot`), обновляется «тиком», привязанным к `FestivalClock`. Источник значений выбирается режимом (`source`):

### A. Детерминированная кривая распродажи + шум (`sim_curve`) — для разработки/демо

У каждого концерта — кривая распродажи `sold(t)` как функция «времени до концерта»/фазы продаж:
- базовая форма (например, S-кривая: медленно → ускорение ближе к дате);
- модификаторы популярности: хедлайнеры (`Artist.is_special`), редкие авторы, прайм-тайм вечера → раскупаются раньше/полнее;
- небольшой воспроизводимый шум (`seed`).

`tickets_left(concert, t) = max(0, capacity − sold(t))`. Детерминирована и воспроизводима, реалистична («популярные уходят раньше»), управляема параметрами. Заменяет случайный затирающий эмулятор v2.

### B. Реплей реальных покупок (`sim_replay`) — реализм и пост-фактум аналитика

Берём `Purchase.purchased_at` из CRM-выгрузки как фактический таймлайн продаж:
`tickets_left(concert, t) = capacity − |{покупки концерта с purchased_at ≤ t}|`.
- Максимально реалистично; полезно изучать «как и что продавалось» (этот режим ты отметил как ценный для аналитики).
- Требует, чтобы в выгрузке были даты покупок (у `Purchase` есть `purchased_at`).

### C. Импорт из CRM (`crm_import`) — продакшн-путь

Периодически загружаем файл с остатками (а позже — запрос по API) → обновляем `ConcertAvailability`. Подробности импорта — [05](05-architecture-and-platform.md#импорт-данных-и-crm).

> Режимы переключаются настройкой; A/B — для дев/демо/тестов и аналитики, C — для реального фестиваля. Все три пишут в одну таблицу состояния + снапшоты, поэтому остальной код (фильтр наличия в [03](03-route-engine.md)) одинаков.

## Тик и кто его двигает

«Тик наличия» и «тик уведомлений» дергает лёгкий планировщик (APScheduler / фоновая задача FastAPI — без брокера, [05](05-architecture-and-platform.md#уведомления-outbox)). Частота реального тика фиксирована (например, раз в N сек), а **виртуальный** прошедший интервал берётся из `FestivalClock` — поэтому в `accelerated` один реальный тик продвигает наличие/напоминания на `K·N` виртуальных секунд. Это и есть «ускоренный таймер»: весь жизненный цикл продаж и напоминаний прогоняется за минуты.

> **Один тикер на инстанс, а не на воркер.** При `uvicorn --workers > 1` планировщик не должен тикать в каждом процессе (иначе двойные пересчёты и двойные письма). Решение: вынести планировщик в **отдельный процесс/сервис** (`scheduler`), либо выбрать лидера через advisory-lock в Postgres (`pg_try_advisory_lock`). Тики идемпотентны: повторный тик на ту же виртуальную метку не плодит дублей (наличие пересчитывается в состояние, постановка уведомлений защищена ключом идемпотентности — см. [05](05-architecture-and-platform.md#уведомления-outbox)).

При каждом тике в `on_sale`/`festival`:
1. Пересчитать наличие на `clock.now()` (по активной модели), записать `ConcertAvailability` + `AvailabilitySnapshot`.
2. На изменившихся концертах опубликовать доменное событие `AvailabilityChanged` ([02](02-domain-model.md)), которое: инвалидирует разделяемый кэш «доступных дневных маршрутов» и порождает `availability_alert` для затронутых листов.
3. Поставить в outbox уведомления, у которых наступило время (см. [05](05-architecture-and-platform.md#уведомления-outbox)).

## Пульт эмуляции (admin)

Экран только для `admin`:
- Режим часов (real/offset/accelerated), сдвиг Δ, скорость `K`; «прыжок» к дате/фазе (offset на конкретный день).
- Режим наличия (`sim_curve` / `sim_replay` / `crm_import`) и его параметры (seed, форма кривой / выбор CRM-выгрузки).
- Кнопки: «сделать тик», «сбросить наличие к старту продаж», «прогнать продажи до даты X».
- Индикатор: текущая виртуальная дата, фаза, сколько концертов в продаже.

## Что это даёт

- Дев/демо в любой точке таймлайна без ручного дёрганья кнопок (как в v2).
- Тест уведомлений и нагрузки в «дни фестиваля» за минуты (accelerated).
- Воспроизводимость (детерминизм A, реальные данные B).
- Реальные данные не затираются (история в снапшотах; продакшн-наличие — отдельный `source=crm_import`).
