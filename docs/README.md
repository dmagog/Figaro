# Figaro v3 — спецификация

Это набор документов для **переписывания сервиса Figaro с нуля**. v2 (текущий код в этом репозитории) служит источником данных, UX-референсом и набором уроков — но v3 строится заново, продуктово, с чистой архитектурой.

> Контекст: фестиваль камерной музыки. ~100 концертов по 45–60 мин на 7–10 близко расположенных площадках, 3 дня, билет ~200 ₽. Зритель собирает из этого разнообразия персональный маршрут — успеть как можно больше ценного, не толкаясь в накладках. Посетителей ~5000.

## Зафиксированные решения (резюме)

- **Фронт:** server-rendered FastAPI + HTMX (без SPA на старте).
- **Идентификация:** аккаунты (логин/пароль).
- **Мультифестивальность:** один DB со скоупом `festival_id`; ровно один фестиваль активен; админ создаёт фестиваль (импорт → предрасчёт всех дней → активация). [ADR 0007](adr/0007-single-db-festival-scoping.md).
- **Роли:** `user / researcher / admin` — реальный RBAC с самого начала.
- **Брокеры:** в MVP нет; уведомления через outbox + лёгкий планировщик, архитектура «готова к брокеру».
- **Движок:** офлайн-предрасчёт дневных маршрутов и признаков (данные стабильны с момента старта продаж); ленивая сборка фестивальных маршрутов по дням; пересчёт только по необходимости.
- **Время:** единый `FestivalClock` (real / offset / accelerated); нигде не зовём системное время напрямую.
- **Наличие билетов:** две модели — детерминированная кривая распродажи (+шум) и реплей реальных покупок из CRM.
- **Процесс:** BDD (behave, русский Gherkin). Сценарии в [`features/`](features/) — контракт, приёмочные тесты и living documentation; каждый этап MVP закрывается своими `@stageN`-сценариями.
- **Сквозное:** приватность/ПДн, безопасность, наблюдаемость, перф-бюджеты, CI и тест-пирамида — в [08](08-cross-cutting.md). Решения зафиксированы как [ADR](adr/).
