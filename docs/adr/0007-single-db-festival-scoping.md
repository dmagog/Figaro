# 0007 — Один DB со скоупом по фестивалю

- Статус: accepted
- Дата: 2026-05

## Контекст

Фестиваль проходит ежегодно; данные каждого года (концерты, залы, программы, маршруты, покупки) независимы. Нужна админ-возможность «Создать новый фестиваль». `show_num` — порядковый номер концерта внутри фестиваля (локальный), значит данные в любом случае скоупятся по фестивалю. Рассматривали: отдельная БД на фестиваль; схема (PostgreSQL schema) на фестиваль; одна БД со скоуп-полем.

## Решение

**Одна БД**; корневая сущность `Festival`; все данные фестиваля несут `festival_id`; ровно один фестиваль `active` для публичного сайта. «Создать фестиваль» = запись `Festival(draft)` → импорт каталога → предрасчёт всех дней → ревью → активация. `User` — глобальный (аккаунт на все годы); `UserPreferences`/`RouteSheet` — в скоупе фестиваля. `crm_show_id` остаётся глобальным (CRM сквозная).

## Последствия

- (+) Простые ops и миграции (одна БД, один набор Alembic-миграций); кросс-фестивальная аналитика возможна позже без объединения баз.
- (+) Архивирование года = `status = archived`, без удаления/переезда.
- (−) Нужно фильтровать по `festival_id` **везде** → выносим в общий слой доступа (репозитории/зависимости), а не «руками».
- (−) Таблицы растут с годами (приемлемо: ~100 концертов и десятки тысяч маршрутов в год; при необходимости — партиционирование/архив).

## Альтернативы (отклонено)

- **Отдельная БД на фестиваль** — лучшая изоляция, но миграции на N баз, маршрутизация подключений и тяжёлая кросс-год аналитика.
- **Схема на фестиваль** — компромисс, но миграции по каждой схеме и маршрутизация `search_path`.
