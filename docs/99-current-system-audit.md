# 99 — Аудит текущей системы (v2)

Зафиксировано на момент аудита. Цель — понять, **что переносим, а что осознанно оставляем позади**. Ссылки на файлы/строки относятся к коду v2 в этом репозитории (`app/...`).

## Что хорошее — переносим (как концепцию)

- **Матрица переходов между залами** `HallTransition` (`models/hall.py:28`) и правила конфликтов (`calculate_transition_time`, `user.py:972`): статусы `overlap / hurry / tight / same_hall / no_transition_data`. Концепция верная — в v3 пороги выносим в конфиг.
- **Concert с настоящими `datetime` + `duration`** (`models/concert.py:11`), M2M артисты/произведения/жанры через link-таблицы. Нормальная основа схемы.
- **Офлайн-предрасчёт маршрутов + ~45 признаков + GMM-кластеры** (`models/route.py`, CSV `RouteRange_with_GMM-.csv`). Это аналитический капитал и основа архетипов.
- **UX-референсы**: маршрутный лист, hero-экраны, анкета холодного старта — см. `docs/images/screenshots/` (`Route list example`, `Route characteristics`, `Cold start anket`, `Concert list shedule`).

## Что НЕ переносим (и почему)

### 1. Случайный эмулятор билетов, затирающий данные
`TicketsService.get_concerts_availability` (`services/crud/tickets.py:63`) на каждый запрос случайно гасит 20–40% концертов и **перезаписывает реальные `tickets_left` случайными значениями в БД**. Прогресс завязан на `_request_counter`, а не на время. Само себя помечает как «временную заглушку». → В v3 наличие управляется детерминированной моделью времени (раздел 04), реальные данные не затираются.

### 2. Две несовместимые ID-вселенные
`Route.Sostav` и проверка наличия используют `Concert.external_id` (`route_service.py:34`), а матчинг покупок — внутренний `concert.id` (`data_loader.py:326,389`). Они молча смешиваются. → В v3 единый внутренний ID + явные FK; `external_id` только для импорта.

### 3. `AvailableRoute` как ручная копия схемы `Route`
Полное дублирование ~45 колонок (`models/route.py:51`), которое надо перестраивать при каждом изменении наличия. → В v3 наличие — это **состояние/фильтр** над маршрутами, а не таблица-клон.

### 4. Дублирование логики между каналами
`routes/user.py` (2378 стр.) и `routes/user/temp_routes.py` (2281 стр.) — почти идентичны; первый используется API, второй — `telegram_service`. Расходятся молча. → В v3 доменная логика в одном месте (services/domain), каналы (web/bot) лишь вызывают её.

### 5. Косметические роли
Поле `User.role` нигде не влияет на доступ; всё гейтится бинарным `is_superuser` (повтор inline-проверки ~50 раз). `observer` имеет нулевой доступ. UI смены ролей нет. → В v3 настоящий RBAC (раздел 05).

### 6. Время напрямую из системы
Везде голый `datetime.now()/utcnow()`. Нет провайдера, нет offset/ускорения. → В v3 `FestivalClock` (раздел 04).

### 7. Только разрушительный полный reload
`init_db(demostart=True)` (`database/database.py:16`) делает drop+create всех таблиц и грузит Excel. Единственный инкрементальный путь — загрузка CSV маршрутов. Импорта наличия/повторного импорта CRM нет. → В v3 разделяем «полный сидинг» и «инкрементальное обновление наличия/покупок».

### 8. Прочий тех-долг
- Хардкод-магия: запас перехода 3 мин, «впритык» 10 мин, дефолт длительности 90 мин, скорость 83.33 м/мин (`user.py`). → конфиг.
- Хардкод-путь `/app/data/ConcertList-good.xlsx`, читаемый дважды внутри `load_artists`/`load_compositions` (`data_loader.py:180,240`).
- FK объявлены, но при загрузке отключены (`session_replication_role=replica`, `data_loader.py:626`) → возможны сироты.
- Реальный баг: `match_percentage` (`user.py:822`) считается только при `len(common)>=2`, а используется всегда.
- Денормализованные строки как ключи: `Route.Sostav="1,2,3"`, `CustomerRouteMatch.customer_concerts` — парсятся регэкспами повсюду.
- Дашборд-статистика мешает реальные счётчики с хардкодом (`home.py:1629` — `notifications:2`, `telegram_stats.sent:15`).
- Маршрутный лист не персистится: пересобирается из `Purchase` на каждый запрос; нет add/remove, нет «корзины». Обещанное на лендинге «исключаем повторы программ» (`index.html:132`) — не реализовано.
- Дублирующая регистрация роутов: `home.py` объявляет пути и **дополнительно** инклудит выделенные роутеры (`home.py:1747`), часть путей затеняется.

## Чего вообще не было (но заявлено/желаемо)

- Интерактивная сборка маршрутного листа и подсказки «что добавить».
- Детектор повторов программ (был только дедуп одинакового `concert_id`).
- Разложение покупок одного клиента по разным людям.
- Ускоренные часы / «дни до фестиваля» / запланированное изъятие билетов / прыжок в «дни фестиваля» — только ручные кнопки «Обновить билеты», дёргающие случайный эмулятор.
- Реальный RBAC, настройки уведомлений (страница — заглушка «🚧 в разработке»).
- **Предрасчёт маршрутов только для одного фестивального дня** (`RouteRange_with_GMM-.csv` содержит `Days = 1`, ~37 946 маршрутов дня 1); дни 2–3 не считались. В v3 предрасчёт обязан покрыть все дни — см. [03](03-route-engine.md#когда-и-для-каких-дней-считаем).

## Вывод

v2 — ценный прототип и источник данных, но архитектурно «вывернут» в сторону админа и накопил дублирование/хардкод. v3 переиспользует **данные, признаки, матрицу переходов и UX-идеи**, но строит чистое доменное ядро, реальные роли, управляемое время и аккуратный импорт.
