# 01 — Продукт и UX

UX-референсы из v2 (сохраняем дух): `docs/images/screenshots/` — `Cold start anket.png`, `Route list example.png`, `Route characteristics.png`, `Concert list shedule.png`.

## Карта сценариев

```
Заход → [Регистрация/вход] → Анкета (4 шага) → Подбор готовых маршрутов (архетипы)
                                                   │
                                       Выбор маршрута → Маршрутный лист
                                                   │                 │
                                        Правка (add/remove,    Показ сложностей
                                        подсказки)             (накладки/переходы/повторы)
                                                   │
                                        [Зона роста] Разложение купленного по людям
```

## Сценарий A. Холодный старт (анкета)

Цель — за ~15 секунд получить осмысленную выдачу. **Правило: спрашиваем только то, что меняет результат.** Остальное (diversity и пр.) выводим из ответов, а не спрашиваем.

4 шага:

1. **Темп** (один выбор): марафон ↔ баланс ↔ расслабленно.
   → задаёт целевое число концертов в день и терпимость к переходам/ожиданию (вес комфорта).
2. **Дни и окна доступности** (чипы): какие из 3 дней, утро/день/вечер.
   → **жёсткий фильтр** кандидатов. Самый сильный и дешёвый сигнал; в v2 его не было.
3. **Вектор интереса** (один выбор): «открывать новое» ↔ «глубже в любимое».
   → вес «разнообразие/глубина» vs «знакомые авторы/жанры».
4. **Любимые авторы/жанры** (опционально, можно пропустить).
   → **бонус в score, не фильтр** (чтобы не обнулять выдачу при редком вкусе).

Ответы сохраняются в профиль (`UserPreferences`, см. [02](02-domain-model.md)) и могут быть изменены в любой момент. Маппинг ответов в веса — в [03](03-route-engine.md#анкета-и-веса).

> Улучшение относительно v2: там анкета собирала `priority/min_max_concerts/diversity/composers/artists`, но движок реально использовал только число концертов и `priority`; остальное — `# TODO`. В v3 каждый из 4 вопросов привязан к конкретному множителю/фильтру.

## Сценарий B. Подбор готовых маршрутов

После анкеты показываем **не плоский список из тысяч**, а несколько **архетипов** (см. [03](03-route-engine.md#архетипы)):

- 🏃 **Марафон** — максимум концертов.
- ☕ **Комфортный** — минимум переходов/ожидания, без спешки.
- 🧭 **Исследователь** — максимум разнообразия жанров/авторов.
- 🎯 **Глубокое погружение** — один композитор/жанр/тема.

Под каждым архетипом — top-k конкретных маршрутов (top-k берётся без перебора триллионов комбинаций, [03](03-route-engine.md#сборка-фестивальных-маршрутов)). Карточка маршрута показывает: число концертов, дни, время в пути/ожидании, стоимость, ключевых авторов, «характеристики» (как `Route characteristics.png`).

## Сценарий C. Маршрутный лист

Центральный артефакт. **В отличие от v2 — это персистентная сущность** (`RouteSheet`, [02](02-domain-model.md)), а не пересборка из покупок на лету.

Два режима на одном движке (как договорились):

- **Готовый → правка.** Зритель берёт маршрут из подбора, тот копируется в его лист, дальше правит.
- **Сборка с нуля + подсказки.** Пустой лист; зритель добавляет концерты, система подсказывает релевантные кандидаты и предупреждает о сложностях.

Операции над листом:
- `add(concert)` / `remove(concert)` / `reorder` (порядок выводится из времени, ручной reorder обычно не нужен).
- **Подсказка «что добавить»**: кандидаты, которые *по времени и переходам* помещаются между/после уже выбранных (см. [03](03-route-engine.md#подсказки-дополнения)). Кандидаты ранжируются по тем же весам анкеты.
- Каждый концерт в листе можно «закрепить» (не предлагать замену) — пригодится при пересчётах наличия.

### Показ сложностей (difficulties)

Между соседними концертами показываем «переходную карточку» со статусом (концепция из v2, пороги — конфиг, [03](03-route-engine.md#правила-конфликтов)):

| Статус | Когда | UX |
|--------|-------|-----|
| `ok` | времени с запасом | зелёный |
| `tight` | впритык (в пределах буфера) | жёлтый, «успеваете, но впритык» |
| `hurry` | нужно поторопиться | янтарный |
| `overlap` | концерты пересекаются по времени **или** перехода физически не хватает | красный, блок только при ручной попытке создать невозможное |
| `no_data` | нет данных о переходе между залами | серый/красный, явно сообщаем |
| `same_hall` / `same_building` | тот же зал/здание | зелёный, перехода нет |

**Повторы программ.** Если добавляемый концерт повторяет уже виденную программу (та же программа/произведения, что в другом концерте листа) — помечаем «вы уже видели эту программу», но не запрещаем (политика «гибко по типу»: накладки блокируем при невозможности, повторы — помечаем). Детектор повторов — новая фича (в v2 был только дедуп одинакового концерта).

> Нюанс из обсуждения: в **предлагаемых** маршрутах накладок и невозможных переходов нет по построению. Сложности возникают в режиме ручной сборки и при разложении уже купленных билетов.

## Сценарий D. Разложение купленного по людям — зона роста

Один клиент CRM часто покупает билеты **на разных людей**, поэтому его покупки содержат пересекающиеся по времени концерты (для v2-матчинга это выглядело как один противоречивый маршрут).

Фича: взять покупки клиента (из CRM) и **разложить их на несколько непротиворечивых маршрутных листов** («лист для себя», «лист для мамы»…). Алгоритм: раскраска графа конфликтов / разбиение на минимальное число совместимых по времени подмножеств; зритель правит вручную. Спецификация алгоритма — позже; в MVP не входит, но доменная модель `RouteSheet` должна допускать несколько листов на пользователя.

## Сценарий E. Просмотр расписания

Полное расписание концертов (как `Concert list shedule.png`) с фильтрами (день, зал, жанр, наличие). Из расписания можно добавлять концерты в лист. В MVP — упрощённый список с фильтрами.

## Не-цели UX в MVP

- Платёж/покупка билетов в Figaro (билеты покупаются во внешней системе; Figaro планирует, наличие импортирует).
- Сложные дашборды (исследователь — позже).
- Мобильное приложение (web + HTMX адаптивно).
