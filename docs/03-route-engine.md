# 03 — Движок маршрутов

## Фундамент: маршрут = путь во времени, а не подмножество

Концерт `B` достижим после `A`, если `B.starts_at ≥ A.ends_at + transition(A.hall, B.hall)`. Если построить граф (узел = концерт, ребро = «успеваешь перейти»), он **ацикличен** (рёбра только вперёд по времени). Маршруты — пути в этом DAG. Это сразу убирает мнимую астрономию «2^100».

## Уровни

```
Концерты дня → DAG достижимости → дневные маршруты (предрасчёт) → признаки → архетипы
                                                                          │
Анкета → веса ───────────────────────────────────────────► ранжирование top-k
                                                                          │
Фестивальный маршрут = ленивая комбинация дневных (НЕ материализуется)
```

## Дневной маршрут (предрасчёт)

Данные стабильны с момента старта продаж → считаем офлайн, пересчитываем по необходимости (форс-мажор).

1. Построить DAG достижимости для каждого дня.
2. Перечислить дневные маршруты (пути). 37k/день для текущего набора — нормально хранить.
3. Для каждого посчитать **аддитивные агрегаты** (concerts, halls, show/transition/wait minutes, cost_kopecks, hall_changes) и **признаки** — четыре канонических: `comfort` (комфорт), `diversity` (разнообразие), `depth` (глубина), `intellect` (интеллект); квантиль-нормировать (`*_qnorm`).
4. Кластеризовать в архетипы (GMM, как в v2).
5. Сохранить в `DayRoute` (+ `DayRouteConcert`).

**Pareto-отсев перед хранением (улучшение):** дневной маршрут, доминируемый другим по всем осям (≥ концертов, ≤ переходов, ≤ ожидания, ≥ разнообразие), выкидываем. Резко чистит набор и выдачу.

**Защита от взрыва перечисления.** Число путей в DAG растёт экспоненциально при ослаблении ограничений. Поэтому: (а) кап на длину/количество маршрутов (beam при перечислении), (б) DAG строится только из «проходимых» рёбер, (в) предрасчёт — офлайн-batch с лимитом времени/памяти и алертом, если набор выходит за ожидаемый порядок. Горячие выборки опираются на индексы (`DayRoute.festival_day_id`, `DayRouteConcert.concert_id`, `DayRouteConcert.day_route_id`) — см. [02](02-domain-model.md#индексы-горячие-пути).

### Когда и для каких дней считаем

Предрасчёт — это **отдельная фаза**, а не часть запроса:

- **Триггер.** Это **шаг 3 конвейера создания фестиваля** ([05](05-architecture-and-platform.md#жизненный-цикл-фестиваля)): после импорта каталога и до активации. При форс-мажоре (замена концерта/исполнителя) — повторный прогон затронутого дня (или всех).
- **Покрываем ВСЕ дни фестиваля.** Batch итерирует по каждому `FestivalDay` **этого фестиваля** (скоуп по `festival_id`): DAG → перечисление → признаки → архетипы → `DayRoute`. Это ключевое отличие от v2, где предрасчитан был **только один день** (`RouteRange_with_GMM-.csv`, `Days = 1`); v3 обязан покрыть все дни фестиваля.
- **Идемпотентность.** Повторный прогон детерминированно перезаписывает `DayRoute` соответствующего дня; незатронутые дни не трогаем.
- **Наблюдаемость.** Логируем число маршрутов по каждому дню; алерт, если набор выходит за ожидаемый порядок (связано с «защитой от взрыва»).
- **Связь с фестивальной сборкой.** Только когда дневные маршруты есть по всем дням, ленивая комбинация по дням (ниже) может строить полноценные многодневные фестивальные маршруты.

## Правила конфликтов

Единая функция `evaluate_transition(prev_concert, next_concert) -> Status`. Пороги — **в конфиге** (в v2 были хардкодом):

```toml
[routing]
buffer_tight_minutes   = 10   # «впритык» сверх времени перехода
buffer_overlap_slack   = 3    # допустимый дефицит перед статусом overlap
default_concert_minutes = 90  # если длительность неизвестна
walk_speed_m_per_min   = 83.3 # для оценки пешего перехода при отсутствии в матрице
```

**Резолв `walk`** (время перехода, мин): сначала из матрицы `HallTransition`; если пары нет, но у обоих залов есть координаты — оценка `walk = round(distance(lat,lon) / walk_speed_m_per_min)`; иначе `walk = None`. Так `walk_speed_m_per_min` из конфига реально используется (а не висит мёртвым параметром).

Логика (`gap = next.starts_at − prev.ends_at`, в минутах):

| Условие | Статус |
|---|---|
| `gap < 0` | `overlap` (накладка по времени) |
| `prev.hall == next.hall` или `walk == 0` | `same_hall` |
| `walk is None` (нет в матрице и нет координат) | `no_data` |
| `walk == 1` | `same_building` (то же здание, переход тривиален) |
| `gap < walk − buffer_overlap_slack` | `overlap` (перехода физически не хватает) |
| `gap < walk` | `hurry` |
| `gap < walk + buffer_tight_minutes` | `tight` |
| иначе | `ok` |

Полный перечень статусов: `ok`, `tight`, `hurry`, `overlap`, `same_hall`, `same_building`, `no_data` (единый словарь для [01](01-product-ux.md), фич и UI). Дневные маршруты при предрасчёте строятся только из «проходимых» рёбер (`ok/tight/same_hall/same_building`); `overlap` и `no_data` в предложениях не появляются. `hurry`/`tight` допустимы, но штрафуют `comfort_score`.

## Анкета и веса

Ответы 4 шагов ([01](01-product-ux.md)) → параметры ранжирования:

| Шаг | Влияние |
|---|---|
| **Темп** (марафон/баланс/расслабленно) | целевое `concerts/day`; вес комфорта `w_comfort` (расслабленно ↑); терпимость к `hurry/tight` |
| **Дни/окна** | **жёсткий фильтр** кандидатов по `festival_day` и `time_window` |
| **Вектор интереса** (new↔deep) | баланс `w_diversity` vs `w_depth` |
| **Любимые авторы/жанры** | аддитивный **бонус** `+b·overlap(favs, route)` (не фильтр) |

Скор маршрута считается на **квантиль-нормированных** признаках (`*_qnorm` ∈ [0,1]), а не на сырых — иначе шкалы (минуты, доли, баллы) несопоставимы:
```
score = w_comfort·comfort_qnorm + w_diversity·diversity_qnorm
        + w_depth·depth_qnorm + w_intellect·intellect_qnorm
        + bonus_favorites
```
веса нормированы (Σw = 1), дефолт «баланс» = равные; `bonus_favorites` — небольшая надбавка вне суммы. Фильтры (дни/окна) применяются ДО скоринга. Конкретные значения весов и `concerts/day` по темпам — в конфиге.

## Сборка фестивальных маршрутов

Ленивая, без полного перебора.

Фестивальный маршрут = выбор по одному дневному маршруту из 1–3 дней. Полное произведение — десятки триллионов; **не материализуем**.

Ключ: дни **независимы** (ночь между ними, нет переходного ограничения). Значит:
- **аддитивные** признаки фестивального маршрута = сумма дневных (cost_kopecks, concerts, show/transition/wait minutes);
- **множественные** (diversity, доля редких авторов) = пересчёт по **объединению** концертов.

Алгоритм выдачи top-N фестивальных маршрутов:
1. По каждому дню взять отсортированные по `score` дневные маршруты (после фильтров анкеты).
2. **Top-k над декартовым произведением** для аддитивной цели — куча/threshold-алгоритм: `O(k log k)`, без обхода произведения.
3. Сгенерировать `N' = c·N` кандидатов по аддитивному прокси.
4. **Переранжировать** этих `N'` по полной цели с пересчётом неаддитивного разнообразия по объединению.
5. Вернуть top-N, сгруппированные по архетипам.

**Что кэшируется, а что считается на запрос (важно — веса персональны):**
- **Кэш (общий для всех):** множество *доступных* дневных маршрутов с предрасчитанными признаками — зависит только от каталога + наличия, не от пользователя. Инвалидируется при изменении `ConcertAvailability` (см. [наличие](#наличие-как-фильтр) и доменное событие `AvailabilityChanged` в [02](02-domain-model.md)). Кэш — разделяемый между воркерами (Redis или единый фоновый процесс), не in-process (иначе рассинхрон при `--workers > 1`, см. [05](05-architecture-and-platform.md)).
- **На запрос (под профиль весов анкеты):** сортировка дневных по `score`, top-k над произведением и переранжировка — это дёшево (`O(k log k)`) и зависит от персональных весов, поэтому **не** кэшируется глобально. При желании — короткий per-(weights-profile) кэш с TTL.

## Наличие как фильтр

Перед выдачей отбрасываем дневные маршруты, содержащие концерт с `is_on_sale = false`. Фильтр на уровне **дневных** (десятки тысяч), затем комбинируем — а не на уровне триллионов (урок v2). Список «доступных дневных маршрутов» кэшируется и инвалидируется при изменении `ConcertAvailability`.

## Пустая или скудная выдача (релаксация)

Жёсткие фильтры анкеты (день + окно + редкий любимый автор) могут обнулить выдачу. Поведение определено явно (в v2 была стихийная релаксация `min_concerts` — формализуем):

1. Если после фильтров кандидатов нет — **поэтапно ослабляем мягкие ограничения** в фиксированном порядке: сперва целевое число концертов (расширяем диапазон), затем окна времени внутри выбранных дней.
2. **Дни доступности и наличие — не ослабляем никогда** (это физические/жёсткие ограничения; нельзя предлагать концерт, когда зрителя нет, или распроданный).
3. Любимые авторы/жанры — это бонус, а не фильтр, поэтому на пустоту не влияют.
4. UI честно сообщает: «под точные параметры мало вариантов — показали ближайшие», с возможностью смягчить шаг анкеты.
5. Если даже так пусто (например, в выбранный день/окно нет доступных концертов) — показываем пустое состояние с понятным объяснением и предложением изменить день/окно.

## Подсказки дополнения

Для режима ручной сборки и кнопки «что добавить»:
1. Взять текущий лист (упорядочен по времени).
2. Кандидаты = концерты, для которых вставка в какую-либо «щель» даёт статус `ok/tight` со **всеми** соседями (`evaluate_transition`).
3. Отфильтровать `is_on_sale`, исключить уже выбранные.
4. Ранжировать по весам анкеты + пометить повторы программы (`Program.signature` совпадает с уже виденной) как «вы уже видели».
5. Вернуть top-N с пояснением «почему помещается» (где в расписании, сколько на переход).

**Внепрограммные события (off-program) в окнах.** В v2 off-program предлагался в «щелях» между концертами; в v3 он есть в модели ([02](02-domain-model.md)), но **в MVP в подсказки не входит** — чтобы не усложнять движок. Решение зафиксировано: off-program подключается отдельным проходом тем же механизмом «что помещается в щель» (`OffProgram` с `starts_at`/`duration`/`hall_id` оценивается так же, как концерт) — запланировано в зоне роста, помечено `@growth`. Это осознанный выбор, а не упущение.

## Разложение покупок по людям (зона роста)

Покупки клиента → граф конфликтов по времени (ребро = накладка/невозможный переход) → разбить на минимальное число совместимых подмножеств (раскраска/жадно) → создать по `RouteSheet` на подмножество → зритель правит. Не в MVP; модель `RouteSheet` это уже допускает.

## Архетипы

GMM-кластеры из v2 переносим как `Archetype`. Для выдачи каждому архетипу присваиваем человекочитаемый характер и показываем top-k внутри него — так зритель выбирает из 4–6 «характеров», а не из тысяч почти одинаковых маршрутов.
