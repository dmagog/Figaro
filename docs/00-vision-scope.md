# 00 — Видение, принципы, scope

## Видение

Figaro помогает зрителю фестиваля **превратить пугающее изобилие (100 концертов, 3 дня, накладки, повторы, страх упустить ценное) в понятный личный план** — маршрутный лист, который интересно собрать и легко пройти.

v2 начинали «от исследователя-администратора» — чтобы видеть и анализировать все маршруты. Это была инверсия приоритетов. **v3 ставит в центр зрителя.** Аналитика и админство — обслуживающие слои.

## Принципы

1. **Продукт для зрителя в центре.** Каждая фича сперва отвечает на вопрос «как это помогает зрителю собрать свой маршрут».
2. **Быстрый холодный старт.** От захода до первого осмысленного маршрута — секунды. Анкета спрашивает только то, что реально влияет на выдачу.
3. **Прозрачные сложности, а не запреты.** Накладки по времени, нехватка времени на переход, повторы программ — показываем явно и понятно; решает зритель (кроме физически невозможного).
4. **Время — управляемое.** Никакого прямого `datetime.now()`. Всё «сейчас» идёт через `FestivalClock`, что даёт эмуляцию, демо и тесты уведомлений/нагрузки.
5. **Данные стабильны — считаем заранее.** Программа фестиваля известна с момента старта продаж; тяжёлый расчёт маршрутов офлайн, пересчёт только по необходимости (форс-мажор). В реальном времени меняется лишь наличие.
6. **Простота инфраструктуры под реальную нагрузку.** ~5000 зрителей за фестиваль → десятки одновременных запросов. Не тащим брокеры и распределённость, пока нет задачи.
7. **Чистые границы.** Доменная логика отделена от веба и от способа доставки (web/HTMX сейчас, бот/почта потом). Никакого дублирования логики между «каналами» (главный урок v2 — см. раздел 99).

## Персоны и роли

| Роль | Кто это | Что делает в v3 | MVP |
|------|---------|-----------------|-----|
| **user** | Зритель фестиваля | Анкета, подбор маршрутов, сборка/правка маршрутного листа, просмотр сложностей | ✅ |
| **researcher** | Маркетинг/аналитик | Изучает маршруты и продажи, дашборды, фильтры, «интересные факты» для внешних задач | ⏳ роль резервируется, экраны позже |
| **admin** | Оператор системы | Пользователи, системные настройки, запуск пересчётов, **пульт эмуляции** (часы, наличие), импорт CRM | ✅ (минимально) |

RBAC реальный с первого дня (в v2 роль была косметической, всё гейтилось бинарным `is_superuser` — не повторяем). Подробности — [05](05-architecture-and-platform.md#роли-и-доступ-rbac).

## Граница MVP

**В MVP:**
- Жизненный цикл фестиваля: админ создаёт фестиваль → импорт → предрасчёт всех дней → активация (один активный); скоуп данных по `festival_id`.
- Аккаунты (`user`, `admin`), вход по логину/паролю.
- Анкета холодного старта — 4 быстрых шага → веса ранжирования.
- Подбор готовых маршрутов (архетипы) под анкету.
- Маршрутный лист: просмотр + добавление/удаление концертов, показ сложностей (накладки, переходы, повторы).
- `FestivalClock` + детерминированная модель наличия + реплей покупок.
- Пульт эмуляции для админа (фаза, скорость часов, режим наличия).
- Скелет email-уведомлений (через часы; outbox без брокера).

**Откладываем (зона роста):**
- Разложение купленных билетов по людям (CRM) на отдельные маршруты.
- Дашборды и маркетинг-фильтры исследователя.
- Telegram-бот и массовые рассылки (вместе с брокером).
- Полный CRUD-админ по сущностям.
- Live-API интеграция с CRM (на старте — файловый импорт).

## Глоссарий

- **Фестиваль (Festival)** — год проведения как корневая сущность; всё (концерты, маршруты, покупки) скоупится по нему. Хранение — один DB со скоупом `festival_id`; ровно один фестиваль «активен» для публики. Админ создаёт новый фестиваль (импорт → предрасчёт → активация), см. [05](05-architecture-and-platform.md#жизненный-цикл-фестиваля).
- **Концерт** — событие в зале с датой/временем, длительностью, программой (произведения/авторы), артистами, жанром, ценой.
- **Площадка / зал (Hall)** — место проведения; между залами есть время перехода (матрица переходов).
- **Дневной маршрут** — допустимая по времени и переходам последовательность концертов в пределах одного дня.
- **Фестивальный маршрут** — комбинация дневных маршрутов (по 1–3 дням). Не материализуется (см. [03](03-route-engine.md)).
- **Маршрутный лист** — личный план зрителя: выбранные концерты + порядок + сложности.
- **Признаки маршрута** — числовые характеристики (комфорт, разнообразие, «интеллект/глубина», стоимость и т.п.).
- **Архетип** — кластер маршрутов с понятным характером (марафон / комфортный / исследователь / глубокое погружение).
- **FestivalClock** — провайдер времени с режимами real/offset/accelerated.
- **Наличие** — продаётся ли ещё билет на концерт; меняется во времени по выбранной модели.
